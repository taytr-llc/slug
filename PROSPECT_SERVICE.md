# Local prospect authority service (set 19)

This service connects D68 job issuance and birth admission across processes.
The authority keeps one schema-3 registry open and uses one explicitly trusted
node and policy. The daemon binds only a literal loopback address. Deploying
the binary does not start an authority or expose it on the Railway seed.

## Configuration and process ownership

Initialize a dedicated registry with `slugregistry init-birth` as described in
`PROSPECT_BIRTH.md`. Start the authority using:

```text
slugregistryd --db REGISTRY --policy POLICY.json --rpc-config RPC.json --service-config SERVER.json
```

The daemon opens an existing schema-3 registry exclusively. It never creates,
migrates, repairs or clears a store. Stop it before using direct registry CLI
commands or copying the complete directory for backup. Shutdown drains actual
handlers before closing the database, including an uncancellable proof hash.

Every field below is required. JSON rejects duplicate decoded keys, unknown,
missing/null fields, malformed UTF-8 and trailing input. Configuration documents
are bounded to 64 KiB; parse errors redact contents.

Server configuration:

```text
{
  "version": 1,
  "listen": "127.0.0.1:29440",
  "clients": [{"public_key": "COMPRESSED_SECP256K1_HEX", "token_sha256": "SHA256_OF_RAW_TOKEN_HEX"}],
  "max_jobs": 10000,
  "max_records": 10000
}
```

`listen` requires a literal loopback IP and explicit port; port zero allocates
an ephemeral local port. The ready message identifies the actual HTTP origin.
One to 64 clients are permitted, with one credential per public key. Keys and
hashes must be unique. An API token is 32 randomly generated bytes encoded as
64 hexadecimal characters. The server stores SHA256 **over the decoded 32
bytes**. This token grants API access; it is not a wallet private key,
checkpoint seed or node RPC credential and cannot sign an admission.

`max_jobs` and `max_records` are required positive storage capacities, at most
one billion each. Counts survive restarts; expired jobs are not pruned. These
are operator resource limits, not product caps on signing prospects. Operators
must intentionally increase capacity or provision storage when needed;
restarting cannot erase the count. Historical receipt recovery remains
available at the admission capacity.

Client configuration:

```text
{
  "version": 1,
  "url": "http://127.0.0.1:29440",
  "token": "RAW_32_BYTE_TOKEN_AS_HEX",
  "ca_certificate": ""
}
```

Plain HTTP requires a literal loopback address. The client also supports
verified HTTPS for a separately administered TLS endpoint; this does not
expose the bundled daemon. A nonempty PEM CA set replaces system roots.
No insecure TLS, environment proxy, redirects or automatic retries are used.
URLs cannot contain credentials, query, fragment, or a non-root path. Keep
API and RPC configuration private. The repository supplies no real credentials.

## HTTP contract, version 1

Both endpoints require `Authorization: Bearer TOKEN` and
`Content-Type: application/json`. Authentication precedes request-body parsing,
database access, RPC and Argon2id. The credential's public key must match the
request's key before work starts. No Origin/CORS, compression, query-string,
alternative method or extra endpoint is accepted. Host must identify a literal
loopback authority. Proof-specific gym authorization is independently verified.

- `POST /v1/jobs`, body `{"public_key":"..."}`, returns a canonical
  `prospectjob.Job`. Policy is fixed by the operator; context comes from the
  node. The authority generates challenge/time and durably commits issuance.
- `POST /v1/admissions`, body `{"proof":{...},"authorization":{...}}`, returns
  `AdmissionResult`: `version`, `context_source`, `current_node_checked`,
  `authentication`, `birth_rule`, `inserted`, `record`. The registry supplies
  the stored job. New births recheck the node, fixed policy and final expiry.

New admissions report `trusted-node-snapshot`, `current_node_checked:true`,
`inserted:true`. Accepted retries report `historical-receipt`,
`current_node_checked:false`, `inserted:false`, with the original complete
receipt. Both report `authentication:"gym-key-control"` and
`birth_rule:"job-issuance"`. Historical results survive expiry and current
policy/node changes without renewed eligibility. An equivalent valid retry
signature cannot replace the first stored signature or birth.

Error bodies contain only `{"version":1,"error":{"code":"...",
"outcome_unknown":false}}`. Codes and HTTP statuses:

| Status | Codes |
| --- | --- |
| 400 | `invalid_request` |
| 401 | `unauthorized` |
| 403 | `forbidden` |
| 404 | `unknown_job` |
| 409 | `expired` |
| 413 | `too_large` |
| 422 | `rejected` |
| 429 | `rate_limited` |
| 503 | `busy`, `capacity`, `unavailable`, `outcome_unknown` |

Raw storage, node, body and credential details are never returned. An uncertain
write poisons the handle and reports `outcome_unknown:true`; the operator must
stop and reopen it before retrying. A cancelled connection or lost response
can race a commit. Retain the job, proof and authorization, then replay
identical evidence to recover the first receipt. Transport failure does not
mean no birth was recorded. Lost issuance output can strand an unused job;
requesting a fresh job is safe and consumes another durable slot.

The client strictly validates returned jobs and complete nested receipts,
including work/DNA, job/proof/key bindings and birth interval. It pins the
expected job supplied to `Submit`; old policy is accepted only in a valid
historical receipt for that job. It cannot independently prove the authority's
wall clock, durable storage or honest classification. D68 still trusts those.

## Bounds and integration

Requests are bounded to 64 KiB and responses to 72 KiB. The server permits 16
connections and one active operation with no application queue. Per credential,
issuance permits one request/second with burst two; admission permits four per
second with burst four. The permit remains held while hashing, performing RPC,
writing or encoding. Header/read/write/idle timeouts are 5/10/35/15 seconds;
header limit is 8 KiB and operation context is 30 seconds. Final expiry is
checked after verification and the node guard; arrival before expiry grants no
grace. Cheap test PoW is rejected before the service listens.

Public-input CLI transport commands:

```text
slugregistry issue-job-service --service-config CLIENT.json --policy POLICY.json --public-key HEX
slugregistry record-job-service --service-config CLIENT.json --policy POLICY.json --job JOB.json --proof PROOF.json --authorization AUTH.json
```

`SignAndSubmit` lets a client sign automatically in memory through a callback
under D44. It returns the generated authorization even on submission failure,
for exact retry. It never reads keys or adds player prospect selection.
Real wallet custody/login/export and automatic mining/renewal remain separate.

A job is not a full payable block template: the context API omits coinbase
value/auxiliary data, transaction bytes and witness commitment. The next miner
slice must construct valid blocks and handle prospect shares and block-target
wins. Submitting a winning block changes the parent and affects admission
ordering. That needs explicit handling; this service adds no eligibility rule.
