# Native DAILY paid-wallet acceptance draft

This is a new, source-only acceptance execution over the **original stopped
Set82 attempt5 paid account, wallet, remote attachment and operator stores**.
It does not renew attempt5's completed deadline or reuse its generation1–3
lifecycle authority. Root owns builds, source selection, host/node starts and
all execution. No prior file or product source was edited by this draft.

The smallest useful positive is a healthy original watched wallet plus the
installed native `RemotePoolController` payout methods. Repeating mining,
issuance, coinbase maturity, or payment would add no coverage to this adapter.
The fixed original payment is1980000000 atoms at output0, funding heights63/64,
fee209, change19999791, confirmed at165. Those amounts come from the already
qualified independent two-reward recipe; the exact original txid/output is
correlated to the retained public Set82 money and wallet evidence.

## Required execution selection

1. Root first qualifies the narrow exported-busy correction: the selected
   adapter maps only exact private `errRemotePoolCredentialBusy` to existing
   public `pilot.ErrRemotePoolBusy`. An in-flight read occupies its credential
   gate, so native polling needs this classification. No string matching,
   delayed-poll workaround, blanket-error retry or other error relaxation.
2. Original attempt5 controller/account/wallet and remote attachment are closed.
   Reuse those same paths and current database histories, not fresh copies of a
   pre-payment wallet. The published incrementing256 fixture is the only account.
   Original wallet history and exact outbox/request rows must be independently
   checked before/after by the existing root fixture catalog and closed auditors.
3. The exact original selected remote config, credential files, RPC selection,
   recipient controls, CA/key pins and attachment markers remain in place and
   unmodified. Credentials and certificates must still be valid. Root may inspect
   their protected expiry through existing authorized tools; this review does not
   read them. Expiry is a precondition failure, not authority to rotate or repin.
4. Root restores the original isolated normal nodes/bridge and original operator
   with the same data/configuration, through a **new bounded execution identity**.
   Use existing qualified normal binaries and original supervision as applicable.
   Old attempt5 lifecycle sources have an expired absolute deadline and only
   three generations: do not edit or restart that execution. Any necessary new
   host lifecycle wrapper must be independently selected and retain actual child
   Wait/exit/joins. No reset, bootstrap, new wallet, new block, new Issue or Start.
5. Keep the chain at165 and remain on the original completed UTC payout day,
   November21. Original completed-day refresh may change report timestamps and
   revision, but it must not create another batch or signed body. Root's closed
   financial before/after audits must compare the exact original batch, credits
   and source claims, independently of this helper. Stop rather than crossing
   midnight. No direct `RunDaily`, manual payment, or scheduler test clock.
6. Root supplies a fresh absolute helper deadline at most300seconds in the
   future and a fresh public report path in an existing owned0700 evidence
   directory. The deadline covers both original-owner generations and cleanup.
   Existing Open60s, Login90s, Snapshot20s and read30s limits remain bounded by
   that shared deadline; cleanup retains original Logout30s/Close and fails if
   final evidence exceeds the shared deadline. The outer process owner must
   still record exit, signal/kill if necessary, and actual join; report booleans
   alone never substitute for that owner.

If these original roots cannot safely reopen under their unchanged selection,
this reuse path is blocked. A new local normal-PoW financial fixture is a separate
fallback requiring root selection, not an implicit reset or new payout here.

## Executable draft

`main.go` is the new direct-native scenario. `observer_support.go` extracts the
unchanged bounded input, snapshot, original-wallet projection and output-parent
helpers from Set82's stopped observer. It does not import or execute that helper.
The module has no absolute replacements; root supplies the same explicit
paired workspace with local root/desktop/wallet version replacements as before.

```text
native-payout-acceptance \
  --owned-root ORIGINAL_ATTEMPT5_ACCOUNT_ROOT \
  --attachment-root ORIGINAL_ATTEMPT5_REMOTE_ATTACHMENT \
  --reference QUALIFIED_17557B28_REFERENCE \
  --remote-config ORIGINAL_PROTECTED_REMOTE_CONFIG \
  --node-rpc ORIGINAL_PROTECTED_WALLET_RPC \
  --pool-credential ORIGINAL_PROTECTED_POOL_CREDENTIAL \
  --admission-credential ORIGINAL_PROTECTED_ADMISSION_CREDENTIAL \
  --prior-qualification ORIGINAL_ATTEMPT5_QUALIFICATION_JSON \
  --prior-money ORIGINAL_ATTEMPT5_PROOF_CONFIRMED_MONEY_JSON \
  --prior-wallet ORIGINAL_ATTEMPT5_WALLET_CONFIRMED_JSON \
  --deadline-ms NEW_ABSOLUTE_UNIX_MILLISECONDS \
  --report FRESH_PUBLIC_REPORT_JSON
```

The three prior public records are exact hash/length pinned in source and in the
manifest. They select the original paid transaction and wallet observation,
not a product-derived new expected economic formula. Private inputs are bounded,
kept by identity and rechecked; no token or private-input hash is written to the
public report. Root identities are canonical, existing, owned0700 and retained.

For each of two physical owner lifetimes:

- Open the exact original controller stopped and signed out; login through its
  real fixture account/vault and obtain its real healthy watched schema14 wallet
  and View. Require height165, ready, spendable1980000000, zero immature and
  unconfirmed, records2/pending0, zero worker attempts/hashrate.
- Admit fresh payout read sequence1. Cancel the successful **admission caller's**
  context immediately; its accepted read must finish under its original bounded
  attachment lifetime. Poll only that sequence; only exported exact busy is
  retried within the existing30second poll context. A failed read job fails this
  attempt; there is no automatic refresh/new-job loop.
- Require exact source/settlement/recipient/profile/config/original View binding,
  original complete one-batch history, exact paid output and zero remaining
  confirmed/available/reserved amounts. A new revision/dated observation is
  permitted; balances/items/recorded state cannot change.
- Call Cancel on the **completed** job and require its capture unchanged. This
  proves idempotent completed cancellation through the real owner. It does not
  claim a blocked HTTP cancellation barrier; deterministic concrete-TLS component
  tests remain the evidence for that separate case.
- Admit sequence2 for the exact retained first window. Require the same capture
  and item bytes. There is only one global batch, so no invented nonterminal
  cursor or multi-page traversal is claimed. Stop the already stopped original
  controller, then require that the dated capture remains exactly readable.
- Recheck the same original wallet balance; Logout and Close, recording both
  outcomes. Never retry a failed Close or replace a failed owner.

After the first lifetime, physically reopen those same roots. Require a new
ViewID for the same original account/authority/gym/generation and refuse the
closed first View. New sequence1 starts only in this new owner; it must return
the same paid output and balance. No old capture is adopted across owners.

## Evidence and limits

One exclusive public report is bounded at256KiB and contains both original
Views, wallet observations, exact native read/capture DTOs, Stop/Logout/Close
results and input/root-identity checks. The native capture DTO is **not** a new
shipping wire protocol; its embedded existing page retains decimal-string money
and cursors. A successful report requires exit0 and original process join plus
the separate unchanged financial/outbox/history and node/host cleanup evidence.

This closes the healthy native positive, cached one-window replay, completed
Cancel, Stop retention and same-root reopen. It does not qualify live-worker
credential borrowing, real blocked-HTTP cancellation, nonterminal history,
wallet activity/output APIs, UI/bridge serialization, long-lived credentials,
general capacity or release readiness. No new product capability is exposed.
