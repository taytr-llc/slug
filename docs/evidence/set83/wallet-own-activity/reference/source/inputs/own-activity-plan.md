# Next DAILY wallet slice: owned activity and selected payout output

Source-only proposal after the first selected DAILY balance/history pipe and panel. No implementation, execution, schema change, navigation change, or new financial policy is included here. The same original recoverable RemotePoolController, attachment, schema14 wallet, recipient and View remain the owners. The first pipe/panel stage must finish qualification separately.

## Existing behavior to reuse

Set67 `pool_payout_controller.go` selects an exact retained history item before calling the original wallet's `ObservePoolPayout`. `wallet_payout.go` retains that wallet, samples its synchronized tip before/after one bounded read, and verifies the selected transaction, output index, integer atoms and recipient script. Its results distinguish wallet-reported unconfirmed/confirmed, verified not-observed, Busy, and unavailable. They do not assert unspentness, payment authority or finality. Its existing five-second, 256-input/raw-size bounds remain unchanged; larger transactions report unavailable rather than silently widening a decoder.

Set70 `wallet_activity_runtime.go` and the wallet's existing atomic OwnActivity reader capture ordinary incoming, outgoing and self-payment records, independently of pool history. They preserve one walletdb read, matching persisted/live wallet and node tip samples, 256 records, 8 MiB aggregate raw bytes, bounded metadata visits, and existing 32 MiB desktop scratch. Existing pure transaction projection and page/detail limits remain the model. These records are never summed to reconstruct spendable balance.

There is one concrete missing reuse branch: `walletRuntime.captureWalletActivity` currently checks only `r.allocation` and otherwise calls the direct schema9 wallet reader. The remote owned session retains `r.allocation2`. Add a narrow dispatch to that exact original `HostedAllocator2.CaptureOwnActivity`, which already checks its original View and guard before/after its atomic read. Release/reacquire the wallet runtime mutex just as the existing allocator branch does. No newly constructed allocator, direct schema14 DB reader, migration or credential getter is needed.

## Small implementation boundary

1. Add selected remote activity types/controller methods under `desktop/pilot/remote_pool_wallet_activity*.go`, with `RemotePoolView` and full selected config/source/original-source/wallet/allocation identifiers. Do not fabricate `ManifestViewPin`, a stable store, or PoolChild. Reuse `walletRuntime.captureWalletActivity` and pure `projectWalletActivity` with the same original runtime/RPC config. Factor a private payload-only cache builder if necessary; do not pass a forged legacy binding to `buildWalletActivityCache`.
2. Add one immutable capture plus one current operation to the original attachment. Admit, publish and disclose through the original local View/recipient fence. Caller-known operation identity is retained before dispatch; exact repeats reconcile that operation, never the latest successful capture. A failed refresh preserves the previous dated capture; successful refresh invalidates its old page/detail selectors. Pages and details select only records retained in that capture. No account lease spans wallet lock acquisition, DB reads, RPC or joins.
3. Add a selected-output method under `remote_pool_daily_observation.go`: accept only original View, retained DAILY capture sequence, exact batch sequence and transaction/output selector. Derive atoms and recipient script from the exact retained First/Current payment row, not caller values. Capture the original page/cache identity, perform the unchanged wallet observation, then recheck original View, selected config, capture identity and membership before publication. Cached stale pool records may be observed as dated records; never replace or refresh them implicitly. An evicted window, foreign tuple or successful intervening refresh refuses before publication.
4. Parent `RemotePoolController` forwards through original admission/View checks; attachment Stop/Logout/Close cancels and joins admitted activity/observation before any wallet teardown. Stop can retain dated successful captures; Logout/Close remove access. Each task has the existing finite lifetime and fixed memory reservation. No Start, Mining lease, address derivation, signing, submission or remote pool audit is triggered by these local reads.
5. Extend the selected concrete helper/bridge and the existing remote wallet section with fixed activity capture/page/detail/cancel and selected-output commands. Freeze a narrow additive wire successor and independent frame/decimal cases first: the current WIRE1 grammar remains strict, and activity's existing larger detail bound must not be squeezed through the 65,536-byte history response or admitted by raising every response cap. Same process, opaque original View and protected selection; no arbitrary RPC/path/dispatcher. Reuse existing wallet-activity rendering structure, with integer amounts and explicit capture dates, rather than adding a page or navigation section.

The UI must keep three facts separate in the existing wallet area: original local spendable/immature/unconfirmed balances; dated pool-recorded earnings/payments; and dated wallet-recorded transaction/selected-output observations. Busy or unavailable does not become zero or not-observed. Changing the selected account/View clears all prior selectors. The final design review remains later.

## Concrete test and acceptance flow

- Reuse independent Set67 selected-output and Set70 own-activity corpora for unchanged transaction/amount semantics. Add only new remote binding/operation/cursor frames and exact scalar/cap maxima; root qualifies independent outputs before golden consumers.
- Real original HostedAllocator2/schema14 fixture: capture through the runtime's new branch, assert exact identity/stamp/records, and refuse the same read through a foreign allocator or revoked original epoch. Preserve the current plain/schema9 and old-allocator branches.
- Deterministic held local-read and tip seams: no account lease across work; changed height or same-height hash, original View/recipient revocation after read, failed publication, caller cancellation, Stop and Close join. Cancellation cannot preempt a walletdb lock; the owner must still join it before unload. Repeated and old operation selectors cannot start or disclose a replacement task.
- Selected payout membership: exact First and Current rows accepted; wrong capture/batch/tx/output/amount/script, an evicted window and intervening successful refresh refused. Older stale capture observation stays labelled dated. Wallet Busy/unsynced/malformed/absent/confirmed remain distinct; payment/accounting files and signing/broadcast counts remain unchanged.
- Bridge/page controls: fixed methods only, exact original View and operation ID, no automatic refresh/Start, signed integer net amount without unsafe Number conversion, bounded page/detail, stale capture kept on failure, old selectors cleared on success/logout, and delayed response cannot replace a newer View.
- Actual native acceptance should reuse an explicitly selected stopped copy of the paid hosted5 schema14 wallet and original remote attachment under fresh valid current credentials/host availability. Open/Login only, wait original wallet READY, capture own activity, locate the known paid transaction/output, compare integer owned output and wallet-confirmation observation with the independent paid fixture, then Stop/Logout/Close and physical reopen with a new View. No mining, new issuance or payment. Save public captures and exact immutable outbox/payment evidence; preserve the original hosted5 evidence. If historical credentials have expired, use the already-approved original rotation procedure for a new selected attempt, never reset clocks or silently adopt inputs.

Completion of balance/history requires both the first DAILY pipe/panel qualification and this original-wallet activity/output acceptance. The present source plan does not claim either runtime result.
